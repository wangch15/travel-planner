## Standards

- `.ai/` 來源與產物有同步；沒有發現來源管理違規。
- 測試沒有刪既有斷言，但新增守門主要驗詞語存在，不能證明流程順序與例外優先權。
  `最高|升級` 即使命中升級段落、混合修改規則全刪也會過；`不確定` 出現在別段也可過。
  第二個測試只要求入口包含「影響／可行性」，沒有驗 README 的正向判準。
  建議測試限定段落並驗條件／動作關係，至少加以下對照情境：
  換照片無行程文字變更仍第三層、票價更新不影響可行性第二層、已過最後入場第三層、
  混合修改採最高層、首次部署必須 preview。文字測試仍不是 agent 行為測試。

## Spec

### 高：固定第三層條件晚於可直接部署的返回路徑

位置：`.ai/skills/tp-ship/SKILL.md`「依序問這三個問題，第一個成立的就是答案」與「一定是第三層的」。
第一問沒有改人會照走的資訊，就直接 ship；但改 theme.css／換照片也常滿足此條件，
後文卻一律列第三層。應先檢查固定第三層條件，再進入第一、二層判斷，避免先返回。
「第一次上線」雖在段首先講清楚，仍宜合併到同一個優先檢查，不維護兩套順序。

### 中：可行性判準未涵蓋「抵達仍營業，但完成不了」

位置：同檔「那天還走不走得通」四條清單。
最後入場早於閉館、最低遊覽時間不足、停留變長而錯過末班車／既有預約，都可能沒有
改停留點間車程、沒有新增前提、也沒有主動改順序，卻使整天不可行。
第二問的總括「可行性沒變」理論上可擋；問題是四條未說明只是最低檢查而非完整清單。
建議明列：檢查從抵達到完成活動、銜接下一段及既有預約／交通截止時間，另涵蓋
已知票額售罄或服務停止。這是具體化既有可行性要求，不建議另加一套分類。

### 中：三處摘要沒有一致表達不可豁免的情況

位置：project-context「三道人類閘門」第 2 條、README「做好之後想改東西呢？」、tp-ship 固定第三層清單。
入口說只改呈現可直接 ship，但 tp-ship 的 theme.css／extra.js／照片都必須 preview；
README 也未提這些例外。第一次上線在 tp-ship 與 README 其他段落仍有要求，不算被完全移除，
但入口摘要遺失該條件，不能宣稱三處說法已完全一致。
建議入口明列「首次／固定第三層例外優先，其餘依影響分類」，README 用白話交代
版面結構、地圖、照片更新要先看過，不複製整份清單。
