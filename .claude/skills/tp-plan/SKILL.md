# tp-plan

## 什麼時候用

環境已經準備好（見 `tp-setup`），使用者要開始規劃一趟行程。

## 核心原則

**先盤點、再問、最後才做。** 不要收到一句「我想去北海道五天」就開始查景點——
先把缺的資訊一次問齊，否則你會查一堆最後用不上的東西。

## 步驟

### 0. 先讀 `trips/_profile.md`

**第二趟開始，有一半的問題不用再問。** 同行的人、體力、飲食限制、行程鬆緊、
住宿等級這些東西跨行程不會變，第一趟問完就該記下來。

```
trips/_profile.md
```

- **檔案存在** → 讀它，下面第 3 步的盤點只針對「這趟特有的」。
  開場先跟使用者確認一次：「上次記的條件是 ⋯⋯，這趟一樣嗎？」
  **不要假設它一定還正確**——小孩長大了、有人開始吃素、長輩加入了。
- **檔案不存在**（第一趟）→ 先盤點與收集條件，**閘門一通過後才建立**，見第 8 步。

格式很自由，但至少要有這幾段：

```markdown
# 旅伴與偏好

最後更新：YYYY-MM-DD

## 同行的人
幾個人、年齡層、體力（一天能走多久、有沒有長輩或小孩要考慮）

## 飲食
不吃什麼、過敏、忌口。**寫在這裡就好，不要寫進資料檔**（見 privacy 規則）

## 交通
自駕還是大眾運輸、有沒有國際駕照、習慣的租車車型

## 行程節奏
想塞滿還是慢慢走、一天大概幾個點、能接受多長的車程

## 住宿
等級與預算感、偏好的房型

## 其他
固定的習慣、雷點、上次哪裡踩雷了
```

**這個檔案不會進入網站產物**（有測試把關），跟 `trips/<slug>/docs/` 一樣是
你的工作區。它會 commit 進使用者自己的私有 repo，所以換一台電腦也還在。

### 1. 確認 slug 並建立行程骨架

先確認這是新行程，與使用者確定 slug（小寫英數與連字號，例如 `kyoto-2027`）。
**先建立骨架，再寫初稿**；`new` 會拒絕既有資料夾，不得先自行建立目錄或寫筆記。
如果同名資料夾已存在，先問是要續做舊行程還是另取名稱，不要刪除或覆蓋。

第一趟：

```
npm run new -- <slug>
```

**第二趟開始，沿用已確認來源行程的偏好設定：**

```
npm run new -- <slug> --from <上一趟的 slug>
```

有多趟而未指定沿用哪趟時，先依 `which-trip` 問清楚來源，不能猜「上一趟」。
`--from` 會帶過來 `lang`、`currency`、`party`、`transport`、`sections`、`theme`、
`basemap`、`region.country` 與 `theme.css`。
**日期、`region.bbox`、標題與 `deploy.name` 不會沿用**，那些每趟都不一樣，
沿用只會讓人忘記改。

**帶過來的是複本，不是連動。** 每趟行程有自己的 `trip.config.json`，所以把新行程的
`party` 從 4 改成 2，**不影響**舊行程，重新 build 出來的舊網站也不變。`--from` 只是
預填，省掉重打一遍；**每一項都還是要跟使用者核對一次**，不要當成已確認的事實。

確認前只允許用 `new` 建立空白骨架，**不得填入正式行程內容**。
骨架建立成功後才進入下一步；全域設定等第 5 步再填。
new 成功後，將先前 setup 的交接補到 `trips/<slug>/docs/status.md`；不要在 new 之前建立它。

### 2. 收初版

使用者可能給你一段文字、一個檔案、幾張截圖，或是用講的。
把它原樣整理成 `trips/<slug>/docs/brief.md` 的草稿，**先不要加你自己的想法**。

### 3. 完整性盤點

對照下面的清單，看初版缺了什麼。**這份清單是提示，不是要照抄的問卷**——
問題由你自己列，只問缺的。

**右欄標「profile」的，`_profile.md` 有就不要再問**，把它當已知條件。

| 要知道的 | 來源 |
|---|---|
| 日期、天數、怎麼抵達與離開 | 每趟都要問 |
| 目的地區域（決定地圖 bbox） | 每趟都要問 |
| 每晚住哪裡：已經訂好的？還是要找？ | 每趟都要問 |
| 一定要去的、絕對不去的 | 每趟都要問 |
| 這趟的預算感 | 每趟都要問（等級偏好在 profile） |
| 交通方式：自駕（租車、國際駕照）還是大眾運輸（pass） | profile |
| 同行人數與體力 | profile |
| 飲食限制與過敏 | profile |
| 行程鬆緊：想塞滿還是慢慢走 | profile |

第一趟沒有 profile，上面整張表都要問。第二趟開始通常只剩前五項。

### 4. 一次問完

把缺的整理成一組問題，**一次問完**，不要一題一題來回消耗使用者耐心。

拿到回答後補齊 `brief.md`，每個區塊標明是：

- **使用者已定，只查核** —— 例如已經訂好的飯店，你只需要確認地址與入住時間
- **請 agent 建議** —— 例如「第三天不知道要去哪」

要找住宿的話，列候選並附官網連結。**你不代訂任何東西**——不訂房、不訂位、
不買票。給連結，讓使用者自己決定、自己付錢。

### 5. 填行程設定

**`deploy.name` 要問使用者。** 骨架預設用 slug，但那一段會出現在他傳給家人的
網址裡（`<deploy.name>.<他的帳號>.workers.dev`），所以填之前先問他想叫什麼。
兩趟共用同一個名字會讓後部署的把先部署的線上網站整個換掉而網址不變——
`check` 與 `ship` 兩道都會擋，但不要走到那一步。

**兩趟可以同時掛在線上**，各自一個網址，互不影響。

然後填 `trips/<slug>/trip.config.json`。幾個要注意的：

- `region.bbox` 是 `[lngMin, latMin, lngMax, latMax]`。把所有目的地包進去，
  四周再留一點邊。太小的話底圖會缺角、座標驗證會擋掉合法的地點。
- `party` 只用來算「N 人約 …」的餐費，`currency` 是金額前綴。
- `sections` 關閉只停用區塊顯示與對應檢查，其他共用資料驗證仍適用。
  build 仍會把全部資料物件內嵌進 HTML，**不是隱私保護**；私人資訊不能留在關閉的區塊。
  **`mapLists` 預設關閉，使用者沒有主動說要做每日 Google Maps 清單就不要開。**
  那是額外的手工（人要先在 Maps 建清單、逐一加地點），不該由你替他決定要做。
- 欄位細節見 `docs/schema/trip-config.md`。

### 6. 寫逐日草案

寫 `trips/<slug>/docs/plan.md`：

- 每天一段：主軸是什麼、大概去哪幾個點、怎麼移動、住哪
- 每天列出**備案**（下雨、走累、店休）與**待確認事項**
- 標出你不確定的地方，讓使用者知道哪些還要討論

這份是給人看的文字草案，**五個資料檔維持骨架，不填正式行程內容**。

### 7. 閘門一：請人確認

**把 `plan.md` 給使用者看，等他確認。**

確認之前：

- `data.js`、`details.js`、`dining.js`、`map-lists.js`、`photos.json` 只保留第 1 步產生的骨架，不能填正式內容
- 不要做深度查核（查營業時間、查路線、查停車場）

原因很簡單：整天的行程順序如果要改，先查好的那些資料有一半會作廢。
先確認骨架，再花力氣填細節。

### 8. 把這趟學到的寫回 `_profile.md`

閘門一通過之後，**趁記憶還新**更新 `trips/_profile.md`：

- 第一趟：把第 3、4 步問到的條件整理成第 0 步的格式，建立檔案
- 之後每趟：**只改永久變了的部分**，順手更新「最後更新」日期

**不要把這趟的行程內容寫進去**——它記的是「這群人是什麼樣的人」，
不是「這次去了哪裡」。

#### 「這趟特有」與「永久改變」要分清楚

`_profile.md` **整個 repo 只有一份，所有行程共用**。把這趟特有的差異寫進去，
下一趟就會用錯的前提開始問。

| 使用者說的 | 這是什麼 | 寫哪裡 |
|---|---|---|
| 「這次只有我跟老婆去」 | **這趟特有** | 那趟的 `trip.config.json` 的 `party`。**不要改 `_profile.md` 的人數** |
| 「這次不租車，坐電車」 | **這趟特有** | 那趟的 `trip.config.json` 的 `transport` |
| 「這次只有兩天，快閃」 | **這趟特有** | 那趟的 `trip.config.json` 的 `dates` |
| 「小孩上小學了，走得動了」 | **永久改變** | 更新 `_profile.md` |
| 「我媽開始吃素」 | **永久改變** | 更新 `_profile.md` |
| 「上次車程兩小時大家就崩潰，以後別排那麼遠」 | **永久改變** | 更新 `_profile.md` |

**判準：下一趟還會是這樣嗎？**

- 會 → 永久改變，更新 `_profile.md`
- 只有這次 → 寫進那趟的 `trip.config.json`，`_profile.md` 一個字都不要動
- **分不出來就問使用者一句**：「這次只有兩個人——以後都是兩個人，還是這次特別？」

## 進度交接（完成或暫停時）

完成、暫停等人或遇到阻礙時，回覆前更新 `trips/<slug>/docs/status.md` 的目前階段、等待確認、阻礙、下一步。
依 `.ai/rules/progress-tracking.md` 只記確知的進度；先更新 status，再執行下節保存，不能把等待當作同意。

## 階段保存（完成條件）

閘門一通過、brief／plan 與 `_profile.md` 更新後，依 `.ai/rules/stage-backup.md` 保存本機 checkpoint 並備份。
每次 push 前重新確認 origin 是使用者自己的私有 repo；備份核對成功，才回報本階段完成並轉 `tp-research`。
失敗或離線就停下來，明說「目前只有本機備份，尚未異地備份」，不要直接當成已完成。

## 完成後

草案確認與階段備份都成功了，接著用 `tp-research` 開始查核並填資料檔。
