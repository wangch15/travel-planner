# tp-ship

## 什麼時候用

資料查完、底圖與照片都好了，要讓使用者在手機上打開。
或者網站已經上線，使用者要改東西。

## 流程

```
npm run check -- <slug>     # 資料驗證
npm run build -- <slug>     # 產出單一 HTML
npm run preview -- <slug>   # 起本機伺服器
```

然後**閘門二**（見下），確認過才：

```
npm run ship -- <slug>
```

把成功輸出的真實網址回報給使用者，不自己拼接帳號子網域；接著做階段保存，尚未備份不能說整個階段完成。

## 進度交接（完成或暫停時）

完成、暫停等人或遇到阻礙時，回覆前更新 `trips/<slug>/docs/status.md` 的目前階段、等待確認、阻礙、下一步。
依 `.ai/rules/progress-tracking.md` 區分等待 preview／認領確認、部署結果與備份阻礙；先更新 status，再執行下節保存。

## 階段保存（完成條件）

第一次部署與每次維護更新之後，都依 `.ai/rules/stage-backup.md` 保存這趟資料、照片及私人筆記；`.local/`、快取與 dist 不入 git。
每次 push 前重新確認 origin 是使用者自己的私有 repo；備份核對成功，才回報部署／維護階段完成。
失敗或離線就停下來，明說「網站已上線；目前只有本機備份，尚未異地備份」，不要為補備份而重新 ship。

## 部署前唯讀查核與本機紀錄

`ship` 使用已安裝的 wrangler 4.135.0，所有查核都在真正部署之前：

1. `whoami --json` 核對登入帳號；多帳號時必須明確指定 `CLOUDFLARE_ACCOUNT_ID`，不猜也不問 stdin。
2. Workers 用 `deployments list --name <名稱> --json` 查目前部署；**未登入、網路錯誤或權限不足就停止**。
   只有明確的 Worker 不存在回應才能新建，不能把任意非零退出碼或空列表當不存在。
3. Worker 已存在，就必須符合本趟本機紀錄的帳號、名稱與上次版本，否則非零退出拒絕覆蓋。
   **沒有相符紀錄就不自動認領**，包含跨 repo 撞名、換電腦、遺失紀錄，以及升級前已部署的網站。

成功後才從 wrangler 輸出記下網址與版本，存到 `.local/deployments/<slug>.json`。
這個位置已 gitignore，不進 git、不進網站；只存必要身分與網址，**不保存登入憑證**、email 或原始輸出。
首次部署前網址尚未知，腳本會明說；之後顯示上次成功的真實網址，不使用 `<你的帳號>` 佔位符。
它不是即時子網域查詢，也不是人類確認；既有 preview 閘門不變。

被擋時：先回報原因，核對帳號與行程名稱。若名稱確實撞到別的網站，請人決定新名稱。
若是自己的既有網站但沒有正式紀錄，走下一節的兩段式認領；不提供自動認領或 force。
不要手寫紀錄、改用裸 wrangler 或刪掉遠端繞過保護。
若顯示「已部署成功，但紀錄寫入失敗」或網址／版本解析失敗，遠端可能已更新，
**不可當成沒部署而盲目重試**。

**Pages 目前不提供這道 Worker 遠端防撞保護**，只保留原本部署流程並保存成功輸出的網址。
查核與部署之間仍可能有其他人同時更新；這不是遠端原子鎖。

## 既有 Worker 的兩段式認領

**agent 不得自行決定認領**，也不能因為 ship 被擋就反射性加旗標。
Cloudflare 只能提供帳號與部署事實，不能判斷「這是不是這趟行程的網站」；歸屬由人決定。

1. 先確認是哪一趟，詢問使用者是否同意做**唯讀查核**。同意後才跑：
   `npm run adopt-deploy -- <slug>`。
   它只呼叫 whoami 與 deployments list，不 build、不部署或改遠端。
2. 把輸出的帳號名稱／ID、Worker 名稱、最後部署時間、版本 ID 與提問**原樣轉述**。
   網址未知就說未知；不能說「這個網址」或自己拼子網域。
   提問是：「Cloudflare 帳號 A 底下已經有 Worker B，最後部署時間是 X，版本是 Y。
   目前實際網址未知。這是你這趟行程的網站嗎？如果不是，請先改 deploy.name。」
3. **等使用者明確確認歸屬**後，才能跑：
   `npm run adopt-deploy -- <slug> --confirm <查核編號>`。
   查核編號不是人已同意的證明，不能省略等待或替他回答。
4. 指令會**重新查核**。行程、帳號名稱／ID、Worker、部署 ID／時間／版本任何一項變更，
   舊收據就失效，必須重新查核、重新請人確認；不是只憑上次看到的資料写入。
5. 成功後建立 `url: null` 的本機認領紀錄，回到正常 preview／ship 保護。
   下一次成功 ship 才補真實網址，並改為一般成功部署紀錄，沒有永久繞過。

已有合法紀錄就**拒絕認領／覆蓋**；損壞紀錄也拒絕，不當作不存在。
不存在的 Worker 走正常新網站流程；多帳號未指定、網路／權限失敗、沒有可辨識部署、
流量分配到多個版本時都停止，不能猜一個版本認領。此指令只支援 Workers，不認領 Pages。

查核收據只存 `.local/deployments/pending/<slug>.json`，與正式紀錄一起 gitignore、不進網站。
只保留查核所需的帳號顯示名稱／ID及部署事實，不存 whoami.email、登入憑證或原始輸出。
查核與寫入不是 Cloudflare 原子鎖；即使認領成功，ship 仍會重新檢查遠端版本。

## 給使用者一個他打得開的預覽網址

`npm run preview` 預設只有**那台電腦**打得開（`localhost:4173`）。
但這個產品是給人在手機上看的——**只用 localhost 預覽，他看不到真正要用的樣子。**

所以預覽時加旗標：

| 指令 | 誰打得開 | 什麼時候用 |
|---|---|---|
| `npm run preview -- <slug>` | 只有這台電腦 | 你自己快速確認 |
| `npm run preview -- <slug> --lan` | 同一個 wifi 的手機 | **預設用這個** |
| `npm run preview -- <slug> --tunnel` | 任何網路，臨時 https 網址 | 他人不在這台電腦旁、或要傳給家人先看 |

`--lan` 會印出 `http://192.168.x.x:4173` 這種網址，**直接把它念給使用者、
請他用手機打開**。同一個網路內的人都看得到，公共 wifi 就別用。

**他說打不開的時候，先看終端機有沒有印出新網址。** 換 wifi、VPN 連上或斷開
都會讓電腦的區網位址變掉，舊網址就失效了；`--lan` 偵測到會印一行
「⚠ 區網位址變了」再給新的。**念新的那個給他，不要叫他重試舊的。**
另外確認他的手機跟電腦在**同一個** wifi——這是最常見的原因。

`--tunnel` 需要 `cloudflared`（免費，**不需要 Cloudflare 帳號**）。
這個網址**關掉指令就失效**，而且拿到的人都看得到——要講清楚。

### cloudflared 沒裝的時候：你幫他裝

跟 Node、git、gh 一樣，**缺的你幫他裝**，不要丟指令叫他自己跑。
差別只在**這個要先問一句**——它是選用的，而且 `--lan` 已經夠用：

> 「要我幫你裝一個小工具嗎？裝了之後我可以給你一個任何網路都打得開的網址，
> 你人不在家也能看、也能先傳給家人。不裝的話，只要你跟電腦在同一個 wifi
> 底下一樣看得到。」

他說好就照他的系統裝：

| 系統 | 指令 |
|---|---|
| macOS | `brew install cloudflared` |
| Windows | `winget install --id Cloudflare.cloudflared` |
| Linux／其他 | 從 https://developers.cloudflare.com/tunnel/downloads/ 取 `.deb`、`.rpm` 或對應架構的 binary |

**裝完自己再跑一次 `--tunnel` 驗證**，不要裝完就說「好了」。

他說不用、或裝不起來（沒有 Homebrew、winget 不存在、公司電腦不給裝），
**不要卡在這裡**：退回 `--lan`，把區網網址給他，繼續往下走。
這只是預覽方式的差別，不影響任何行程內容。

## 閘門二：請人看過才能 ship

**不要自己判斷「看起來沒問題」就部署。**

給他預覽網址（見上一節，優先 `--lan` 讓他用手機看），
**明確請使用者看這幾個地方**：

1. **總覽頁**——住宿色條的天數對不對、每日主軸表的過夜地點對不對
2. **任選一天的詳細行程**——交通段落的時間與距離、餐食安排
3. **任一個燈箱**——點地點名稱打開，看照片、看點、參考資料
4. **手機上實際捲一次**——這是他之後真的會用的樣子

告訴他要看什麼，不要只丟一個網址說「你看一下」。
他不知道該看哪裡，你知道。

### 閘門二適用範圍

**第一次上線一定要走完整的閘門二。** 之後的修改，**看這次改動的影響範圍，
不是看你改了哪個檔案或改了幾個字。**

「換一家餐廳」有可能是換隔壁那家，也有可能是換到城市另一頭——後者會讓那天的
車程、抵達時間與停車全部作廢。用「換餐廳＝小修改」分類會放掉後面那種。

#### 固定第三層：優先檢查

命中下列任一條就直接判為**第三層**，查核後 `build` + `preview`，**人看過才 ship**。
**未命中固定第三層，才進入下面三個問題**；「純呈現」不能豁免這份清單。

- 第一次上線
- 改 `trip.config.json`（日期、bbox、`deploy`、`sections`、主題）
- 加減天數、加減地點、改一天的順序
- 重產底圖或換照片
- 改 `theme.css` 或 `extra.js`（版面結構會變）

#### 依序問這三個問題，找到適用的條件才返回

**1. 有沒有動到任何人會照著走的資訊？**（時間、地點、價格、營業、訂位、交通）

沒有 → **第一層：純呈現修正**。錯字、不改語意的潤飾、排版。
`npm run check` 過就直接 ship。

**2. 動到了，但那天的路線、順序與可行性沒變？**

→ **第二層：事實更新**。更新票價、營業時間、公休日、訂位方式、電話。
**必須查核來源並更新 `checked` 日期**（見 `.ai/rules/research-integrity.md`），
確認之後可以直接 ship。

**3. 路線、順序或可行性變了，或你不確定？**

→ **第三層：結構性改動**。查核後重新 `build` + `preview`，**人看過才 ship**。

#### 「那天還走不走得通」怎麼判斷

下面是最低檢查要求，**不是完整清單**。必須檢查整天從抵達、完成活動到銜接下一段的可行性。
第二層只要命中下面任何一條，就**升級成第三層**；不能因為沒命中列出的例子就認定安全：

- 停留點之間的移動方式、距離或時間會變
- 新的抵達時間落在營業時間之外，或撞到公休日
- 雖仍營業，但已過最後入場，或剩餘時間不足以完成所需停留
- 活動／停留變長，趕不上末班車、轉乘、還車、入住截止時間或後續預約
- 票額售罄、服務停駛或其他已知限制，使原安排不能執行
- 多出原本沒有的前提：要預約、要現金、要證件、要換票
- 當天的順序、過夜地點或主軸會變

例：更新營業時間之後發現原訂 17:30 抵達而對方 17:00 就打烊——
**那不是「改幾個字」，是那天走不通了**，要重新安排並讓人看過。

#### 具體情境：條件 → 層級 → 動作

| 條件 | 層級 | 必要動作 |
|---|---|---|
| 換照片，沒有改行程文字 | 第三層 | 查核後 preview，人看過才 ship |
| 只更新票價，沒有命中例外且整天仍可行 | 第二層 | 查核來源、更新 checked、check 後 ship |
| 抵達仍營業，但已過最後入場 | 第三層 | 重新安排並 preview，人看過才 ship |
| 改錯字加換照片的混合修改 | 第三層 | 採最高層級，preview 後人看過才 ship |
| 首次上線，即使只有文字 | 第三層 | 完整 preview，人看過才 ship |

#### 兩條總則

- **一次改了好幾樣，採其中最高的那一層。**
- **不確定算哪一層 → 當第三層。**

第一、二層**不用每次把人叫回來看 preview**。理由很簡單：他改一行字就要重走
一次完整檢查的話，他會乾脆不改。

但 ship 完**一定要回報兩件事**：改了什麼、網址是什麼。他在手機上就能確認。

## 第一次部署

要先登入 Cloudflare：

```
npx wrangler login
```

**這一步是人類必做的**——會開瀏覽器請使用者授權，你不能代勞。

**沒登入就不要硬試。** 直接回報「需要先登入 Cloudflare，請跑 `npx wrangler login`」
然後停下來等。

新帳號第一次部署會被問要不要註冊 workers.dev 子網域，**選是**。
網址會是 `<deploy.name>.<帳號>.workers.dev`。

## 部署目標

`trip.config` 的 `deploy.target`：

- `workers`（預設）：Cloudflare Workers 靜態資源。**新行程一律用這個。**
- `pages`：**已過時。** Cloudflare 把 Pages 併進 Workers 了，`wrangler pages deploy`
  現在回的是 `.workers.dev` 網址，Cloudflare 自己也建議改用 `wrangler deploy`。
  引擎仍支援它（既有專案還在用），但看到 `pages` 就**建議使用者遷移**，
  步驟見 `docs/schema/trip-config.md`。`adopt-deploy` 不支援 `pages`，
  所以要用認領流程也得先遷移。

**遷移時要講清楚一件事**：舊的 `<name>.pages.dev` 是一個**獨立的 Pages 專案**，
不會跟著更新，會停在最後一次 Pages 部署的內容。所以遷移後線上會同時有新舊兩份。
等使用者確認新網址正常、也把新網址告知拿過舊連結的人，才請他自己去 Cloudflare
刪掉舊的 Pages 專案——**那是花錢帳號裡的資源，你不要代刪**。

## 維護模式

網站上線後，使用者會說「餐廳改成另一家」「第三天加一個點」。流程：

0. **先確定是哪一趟**（有兩趟以上的時候）。`npm run trips` 看候選，
   使用者沒明講就問他——判斷順序見 `.ai/rules/which-trip.md`。
   **這一步不能跳**：改檔案不經過任何指令，猜錯會改到另一趟已經上線的網站。
1. **對應到哪個資料檔**——用 `docs/schema/` 的對照表判斷要改哪一個
   （見 `.ai/rules/data-schema-reference.md`）
2. 改。新增地點的話記得 `details.js` 也要補一筆（非 `hub` 一律要有）
3. `npm run check`
4. 對照上面的「閘門二適用範圍」判斷層級。第三層就 `npm run build` →
   `npm run preview -- <slug> --lan`，把網址給他、請他看過；
   第一、二層直接往下走（第二層記得先查核來源並更新 `checked`）
5. `npm run ship`，然後回報改了什麼與網址
6. **執行上面的「階段保存（完成條件）」**——每次 push 前重新驗 origin 私有，成功後核對遠端 commit；
   線上更新不等於異地備份，失敗不得宣稱這次維護已完成

第一次部署之後 `wrangler` 會把授權存在本機，後續 `npm run ship` **不需要再登入**。
所以「他說要改、你改完就上線」這個循環是走得通的，不用每次都把他叫去按授權。

改動如果牽涉到新地點的座標，而且新座標超出 `region.bbox`，
要放大 bbox 並重跑 `npm run basemap`。
